# Landing page redesign verification

Verified locally on 2 November 2026 against the production build in headless Google Chrome on Windows. No GitHub push or deployment was performed.

## Result and scope

The landing page now uses the original college photograph, a navy college header, the existing theme toggle, four portal cards, and the existing PWA installation hook. Wide screens show four equal cards, tablets show two columns, and mobile shows horizontal cards inside a rounded panel overlapping the photo banner. The mobile menu exposes the same four destinations. The former landing splash delay and animated neural background were removed from this page.

Original routes remain `/student`, `/faculty`, `/hod`, and `/admin`. No route definitions, authentication or authorization code, login components, dashboards, backend APIs, database files, credentials, or other project checkouts were changed. No dependencies were added. No production API or database operations were executed.

## Invisible text: cause and correction

The previous landing cards used a hard-coded dark `bg-[#0B132B]/80` surface. In `src/index.css`, `html.light h1`, `html.light h2`, and `html.light .text-white` force dark navy text with `!important`; the light-theme surface overrides do not match that card background. Switching to Light Mode therefore placed dark titles on dark cards. The same global stylesheet also forces header/main backgrounds and mobile heading sizes.

The replacement uses landing-specific semantic classes and paired surface/text CSS variables driven by the existing theme context. Narrowly scoped overrides counter the existing global header/main/heading rules without editing the shared stylesheet. Reading the saved theme through context also keeps the landing appearance correct when returning from the existing fixed-dark login screens.

## Warnings and environment retries

- Vite reports a JavaScript chunk larger than 500kB: final application bundle approximately 2.23MB before gzip, 522kB gzip. This application-wide bundling warning remains; code splitting unrelated pages was outside the landing-page scope.
- The first `npm` invocation was blocked by PowerShell's policy for `npm.ps1`. Using `npm.cmd` executed the checks successfully without changing that policy.
- The first browser attempt inside the execution sandbox failed to initialize Chrome's GPU processes. Browser verification succeeded after rerunning outside that sandbox with automatic approval. The final run uses its own temporary browser profile and debugging port.
- The first isolated regression-test attempt failed because the sandbox prevented `tsx` from reading the OS user profile (`uv_os_get_passwd` / `ENOMEM`). The same tests passed outside the execution sandbox with automatic approval. No test expectations or application logic were changed to obtain the pass.

Implementation is local and ready for review. GitHub push and Vercel deployment require the user's approval, as requested.
